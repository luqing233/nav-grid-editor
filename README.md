# 终末地地图采集、标定与 2D 网格编辑

本地部署的地图工具，面向终末地地图数据采集与导航网格制作。提供瓦片抓取、
总图合成、像素与世界坐标标定、路径标记、坐标读取和 2D 无高度网格编辑能力。

项目主要面向 Windows。所有运行数据均保存在本地，Web 服务默认仅监听
`127.0.0.1`。

## 快速开始

### 环境要求

- Python 3.12 或更高版本
- [uv](https://docs.astral.sh/uv/)
- Git 和 Git LFS（用于下载预设图片及网格实体）
- 浏览、缩放与编辑预设地图无需地图账号或 Playwright Chromium；只有新增抓取需要浏览器环境

```powershell
git lfs install
git clone --recurse-submodules https://github.com/luqing233/nav-grid-editor.git
cd nav-grid-editor
git lfs pull
git -C assets/nav-grid-data lfs pull
uv sync --locked
uv run nav-grid-editor
```

启动后访问：

<http://127.0.0.1:8764>

根路径会自动跳转到 `/map`。

仓库提供帝江号、四号谷地、武陵三张主图的完整 zoom 4 Q90 瓦片，以及 69 张彩色分层图。
克隆并下载 LFS 实体后即可打开地图、放大、切层和编辑网格，无需再抓取瓦片。
预设来自已保存总图，保持原尺寸和瓦片坐标边界；`assets/tiles/presets/manifest.json`
记录覆盖范围、编码参数及每张瓦片的 SHA-256。已有本地抓取缓存优先于预设。
个人标记、账号凭证和浏览器登录态不随预设分发；缺失层声明仍保留，不宣称覆盖尚未采集的区域。

已有普通克隆可运行 `git submodule update --init --recursive`，再执行上面的两条 `git lfs pull`。
只有需要抓取新区域时，才运行 `uv run playwright install chromium` 并登录官方地图。

维护者可从本地已保存的 zoom 4 总图生成完整预设（缺块从总图补齐，边界不一致会拒绝）：

```powershell
uv run python -m nav_grid_editor.commands.build_presets --output output/new-tile-presets
```

输出必须是新目录，验证完成后再替换发布的预设；生成过程不访问网络或修改原始抓取缓存。

### 常用参数

| 参数 | 说明 |
| --- | --- |
| `--port` | HTTP 服务端口，默认 `8764` |
| `--data-root` | 数据根目录，默认当前工作目录 |
| `--tiles-root` | 瓦片目录，默认 `<data-root>/assets/tiles` |
| `--profile-dir` | Playwright 登录态目录，默认 `<data-root>/browser_profile` |
| `--grid2d-dir` | 2D 网格输出目录，默认 `<data-root>/assets/nav-grid-data` |
| `--position-source` | 玩家位置源：`capture`（抓包后端，默认）/ `ws`（官方地图 WS 兜底） |
| `--capture-url` | 显式指定抓包后端地址；不给就从 `127.0.0.1:8765` 升序探到 `8775` |

示例：

```powershell
uv run nav-grid-editor --port 8764 --data-root D:/nav-data
uv run nav-grid-editor --grid2d-dir D:/nav-data/grids
```

对应环境变量包括 `NAV_DATA_ROOT`、`NAV_TILES_ROOT`、`NAV_PROFILE_DIR`、
`NAV_GRID2D_DIR`、`NAV_POSITION_SOURCE` 和 `NAV_CAPTURE_URL`。

> 本服务默认监听 `8764`，抓包后端默认监听 `8765`，可同时启动。
> 如需调整本服务端口，使用 `--port`。后端换了端口也不用改这里的配置：
> 位置源会从 `8765` 起自动探测（见下文「玩家位置源」）。

> 数据根目录默认取当前工作目录。建议始终在项目根目录启动，或显式传入
> `--data-root`。

## 功能

- **地图抓取**：通过 Playwright 打开游戏地图页面，拦截瓦片请求并实时写入
  浏览器画布。已存在的瓦片直接使用本地缓存；抓取结束后自动合并到
  `assets/tiles/latest`。首次使用需要在弹出的浏览器中完成登录。
- **模拟抓取**：在内存中生成瓦片并实时演示拼接过程，不写盘，也不需要登录。
- **图片格式**：抓取瓦片直接保存响应原字节，按实际内容区分 WebP / PNG，不再将 WebP 转为 PNG。
  已有 PNG 缓存继续读取，不会自动重新下载。总图合成为原尺寸无损 WebP，保存到
  `assets/tiles/maps/<地图>/<zoom>/<地图>_<zoom>.webp`，同名文件覆盖；同名旧 PNG 仍兼容读取，WebP 优先。
  WebP 单边上限为 16383 像素，超限会明确报错，不缩小地图或覆盖原图。
- **官方分层地图**：在已标定的地图上选择官方 `tier` 图层。预设分层图片直接从
  `assets/tiles/layers/` 读取；未缓存的新图首次访问时下载，随后按官方世界 bounds 和当前标定矩阵
  叠到大地图坐标中。点击地图上的“分层入口”标记会直接展开对应的楼层列表。
  没有分层入口标记的区域归入“独立地图”，例如“首墩内部”和“遂明”。
  低缩放时只解码预览图，放大后才切换全分辨率，并只保留当前地图的解码缓存。
- **高性能渲染**：画布只绘制当前可见区域。打开地图时先加载长边不超过
  2048 像素的缩略图，缩放后再按需加载瓦片，避免大图占用过量显存。
  瓦片解码缓存限制为 420 张 / 96 MiB，并且切换到其他地图时立即释放；
  分层图低缩放使用预览版，放大后才加载全分辨率。拖动时 Canvas 位移和重绘
  在同一动画帧提交；界面不使用实时背景模糊，避免拖拽抖动和闪烁。
- **地图标定**：在地图上选择特征点并输入游戏坐标 X/Z。系统使用仿射最小二乘
  和 RANSAC 计算像素与世界坐标的映射，结果写入对应地图的
  `<地图>_<zoom>_mapping.json`。
- **玩家定位**：默认轮询抓包后端 `endfield-capture-backend` 的
  `GET http://127.0.0.1:8765/api/state`，把 `lastPosition` 经 SSE 推给网页，
  显示玩家位置、按坐标自动切楼层，不再依赖本地 WS 中继与账号凭证。
  开启“跟随”时，人物标记保持在编辑器地图中心；可拖动查看其他区域，
  人物再次移动后视口自动回到人物。
  官方地图 WS 实现保留为可选兜底（`NAV_POSITION_SOURCE=ws`）。`POST /api/coords`
  仍保留为外部客户端的备用上报口。详见下文「玩家位置源」。
- **路径标记**：粘贴 `(x,z)` 坐标序列后生成路径折线。起点为绿色，终点为
  红色，途经点显示编号。
- **坐标读取**：点击地图即可查看游戏世界坐标，以及对应的 2D 网格格子坐标。
- **地图标记**：支持抓取认证口径的官方地图标记，包括玩家自建结构。标记筛选
  面板在浏览、网格和取坐标模式下可用，标定模式下隐藏。
- **数据仓库同步**：顶部“同步仓库”按远端 `origin` 默认分支强制覆盖
  `assets/nav-grid-data`，再清除浏览器草稿并重新载入。同步以仓库为准，本地提交、
  未提交修改和未跟踪文件都不会保留。
- **2D 网格编辑**：在已标定的地图上绘制 `Free`、`Blocked` 和未知格子。
  支持画笔宽度、区域框选和批量填充。可开启抓包位置自动标记，把玩家周围自定义半径
  的格子标为 `Free`；仅处理速度不大于 7.5 的有效抓包样本，并对同一层内距离不超过
  7m 的相邻样本沿途补齐空白格。默认按坐标自动判层；选择“按手动选定层采集”后，
  直接写入顶部选定层，无需预先标注高度，并暂停位置流自动切图、切层。属性面板与
  工具栏显示当前写入楼层；手动切层后目标随之更新，跨层不补线。切回自动判层或
  停止采集后恢复位置流自动切换。

### 玩家位置源

位置流默认来自抓包后端 **endfield-capture-backend**：本服务只读它暴露的
`GET http://127.0.0.1:<端口>/api/state`，用标准库 `urllib` 轮询，不新增依赖，
也不启动 / 重启 / 干预后端进程。官方地图 WS（`services/endfield_ws.py`，需要
`configs/hg_content.txt` 里的账号凭证）保留为可选兜底，设
`NAV_POSITION_SOURCE=ws` 切回去。页面上的「位置流」开关、
`GET /api/position/status` 与 `POST /api/position/start|stop` 对两种源是同一套行为。

**端口自动探测。** 没有显式配置 `--capture-url` / `NAV_CAPTURE_URL` 时，位置源从
`127.0.0.1:8765` **升序**探到 `8775`，锁定第一个 `/api/state` 答得像抓包后端的
端口，并把它写进状态（`capture_port`）与页面（「已连接 · 抓包后端 :8766」）。
没找到就在日志和面板里报「已探测 8765–8775」。
只认返回体里有 `flows` / `lastPosition` 的响应，所以本服务自己占着 `8765` 时
（它对 `/api/state` 回 404）不会被误判。探测是只读的，不会启动后端；锁定的端口
掉线后会重新扫描（5 秒冷却），后端换端口 / 重启也能自己接上。
显式给了 `--capture-url` 就钉死用那个地址、不再探测。

**后端必须先于游戏主连接启动。** 会话密钥只在登录握手那一刻出现一次，中途启动的
后端整条流都推不出坐标，只会报「缺少连接起点，请重新启动游戏」——这时重启后端也没用，
只能重开游戏逼出一条新连接。抓包只过滤 30000 / 40000 两个端口。

**判「真的接上了」看 `flows[]`，不看 `lastPosition`。** `lastPosition` 一旦有值就
永远保留，重登录、退游戏都不会清空；`flows[]` 里有一条 `status` 为「正在解码」且
`lastPacket` 还在更新的连接，才算接上。坐标所属的连接已经结束（终态，或超过 30 秒
没收到任何报文）时，这份坐标**不会**画到地图上——它描述的是上一局的位置。

**不要拿「多久没更新」当断线依据。** 上报是事件驱动的：移动中约 0.27 秒一条，
完全静止时没有位置包。所以静止时 `age_seconds` 会变大，但连接仍然活着；界面上的
「N s 前」只作提示。

| `health` | 含义 |
| --- | --- |
| `decoding` | 有条连接正在解码 —— 唯一算「已连接」的状态 |
| `handshake_pending` | 连接已发现，登录握手还没完成 |
| `missed_handshake` | 抓包晚于这条连接（后端被重启过 / 起晚了），只能重开游戏 |
| `no_connection` | 后端在跑，但没有仍在继续的连接 |
| `backend_down` | 连不上抓包后端 |

地图名按后端的场景表来：`mapId` 有值（如 `map02`）就直接用；`levelId` 非空但
`mapId` 为空表示这个场景**不属于任何大地图**（试炼场等），此时不会按坐标范围去猜，
页面明确报「没有网格」，而不是加载一张错的网格。

### 网格状态

| 状态 | 值 | 含义 |
| --- | ---: | --- |
| 未知 | `0` | 尚未探索。下游规划通常将其视为高代价区域 |
| Free | `1` | 已确认可通行 |
| Blocked | `2` | 障碍或不可通行区域 |

不要把未探索区域标记为 `Free`，也不建议将整个未知区域标记为 `Blocked`。

### 分层连接

网格支持类似 PCB via 的跨层连接。每个 grid 仍只保存 `Unknown/Free/Blocked`，
跨地图/分层连接统一保存在 `assets/nav-grid-data/links.json`：

- 起点和终点可以是大地图、分层地图或独立地图；
- 端点保存世界坐标区域（外加所属 `zoom`），不依赖易漂移的格子下标；
- 端点可以带**可选的高度范围** `y_min` / `y_max`（见下）；
- 支持双向、单向、楼梯、电梯、传送、门、绳索和通行代价；
- 编辑器中进入“连接”模式，依次框选起点区域、切换分层、框选终点区域并保存；
  已存在的连接在“分层连接”面板里点“编辑”可以只重选端点，不必删掉重画。

保存时会校验两个端点**各自落在该层的可走格上**：端点整块落在网格范围外、或者
框在一片没涂过的格子上，都会拒绝保存并说明是哪一端、为什么。规划器只认“从可走格
走到可走格”，这种悬空的边等于通向虚空，所以必须挡在写入前。

读取时不改数据：已存在的连接如果端点无效，会在响应里带上 `checks`（`valid` 与
`issue`），编辑器把这条连接标红、列表里也写明原因，由用户决定怎么修。

**端点高度（`y_min` / `y_max`，可选）。** 端点过去只有 X/Z，于是“这两点是不是通向
同一处空间”在格式层面**无法校验**，两层的落差也只能从各自的 `floor_regions` 区间去
推 —— 那是区间不是点，“按落差定价”更无从下手。加上这两个字段后落差是**量出来的**：

- 两端都给 → 响应里带 `checks.drop`（`from_center` / `to_center` / `drop` / 两个
  `span`），编辑器在连接列表里显示“落差 ±N m”；
- 只给一端、或都不给 → `drop` 是 `null`。**不给就是不猜** —— 缺一端时拿层区间凑一个
  数会让人以为它是实测的；
- 两个键要么都给要么都不给，且必须有限、`y_min <= y_max`，否则拒绝保存。

编辑器里那四个 Y 输入框按“起点 / 终点”分成两组，跟着框选阶段走；“用层区间填入”
按钮把该端点所在层**已标的高度区间**填进去（明确是“用层区间填”，不是自动推断 ——
区间是层的属性，不是这个端点的实测高度，所以由人按一下才算数）。

`links.json` 目前是 `schema_version: 3`。v1 的端点没有 `zoom`，读出来会补成 `""` 并按
查询的 `zoom` 解析；v1/v2 都没有端点高度，读出来保持缺失（“不知道”是个合法状态）。
磁盘上的版本等下次写入才升上去。

### 分层导航的约定

规划器按这几条组装分层图，编辑器负责保证产出的数据满足它：

1. **相邻关系只在同一层内成立** —— 每层各自的稠密网格就是该层的可走图；
2. **跨层一律走 `links.json` 的显式边** —— 绝不能把两层按 X/Z 叠起来当邻接。
   同一个 X/Z 上地表和地下都可能是可走的，叠加等于凭空连边；
3. **主地图不挖洞** —— 地表那一格是真实可走的，地下房间在它下面。把主图挖成
   `Blocked` 会删掉真实可走的表面；玩家在哪一层由 `floor_regions` 的 Y 区间判定。

于是「这张图能不能导航」= 所有连接端点有效 + 每处与其它层重合的区域都标了高度区间。
`GET /api/nav-graph?map=&zoom=` 直接把这件事判出来：

```json
{
  "ok": true, "map": "map02", "zoom": "4",
  "ready": false,
  "blockers": ["连接 … 端点无效：…", "重合区 21 格（大地图 / 测试区）…"],
  "tiers": [{"tier_id": "__main__", "grid": "map02_4.grid.npz",
             "origin": [0, 0], "cell_size": 1, "shape": [10, 10],
             "free_cells": [[0, 0]], "floor_regions": []}],
  "links": [{"id": "…", "from": {}, "to": {}, "kind": "stairs"}],
  "cross_tier_edges_from": "links"
}
```

`cross_tier_edges_from` 恒为 `links` —— 响应里不会出现任何隐式跨层邻接。

### 「坐标 → 第几层」的判定规则

`MapService.resolve_tier_by_height(map, x, y, z)` 用各层网格的 `floor_regions` 判断
玩家在哪一层。消费侧（ok-end-field）的跟随器要能独立复刻这条判定，不能依赖编辑器
进程，因此规则与测试向量是**跨仓库契约**：

- 规则说明与全部向量：`tests/data/floor_rule_vectors.json`（`schema_version: 2`）
- 执行器：`tests/test_floor_rule_vectors.py`

两边各跑同一份向量；任何一侧改了行为，另一侧会立刻失败。向量里 `contract: false`
的用例是当前实现的偶然行为（允许改动），失败时只打印提醒、不判失败。

**判定不看 `levelId`** —— 官方那个字段不可信（同一个 levelId 会被多个分层共用、
也可能滞后于玩家实际位置），所以候选层是「这张地图上所有声明了 `floor_regions`
的层」，主图只要自己标了区间同样是候选、没有特权。返回四种结果：

| status | 含义 | 附带 |
| --- | --- | --- |
| `unique` | 恰好一层盖住这点 | `tier_id` 是该层 |
| `ambiguous` | 多层盖住 | `matched` 列出全部，`tier_id` 为空 —— **不替调用方挑** |
| `main` | 兜底大地图 | `reason` = `no_layers`（一层都没标过）/ `no_region_covers`（标了但没盖住这点） |
| `invalid` | 地图名非法或坐标非有限数 | 这条位置消息本身不可用，**不该**据此切到大地图 |

几个容易踩的点（都在向量里）：

- **兜底是主路径，不是边角**：当前 map02 只有 2 段各 39 格区间，所以绝大多数坐标
  都走 `main`。`no_layers` 与 `no_region_covers` 要分开，界面上该说不同的话。
- **只有一个候选层也要它真的盖住这点** 才报 `unique`（v1 里是「单候选无条件
  unique」，那条 wart 在 v2 随 levelId 一起消失）。
- `region.cells` 非空时**先要求命中某个 cell 的 X/Z**，再判外框与 Y；都是闭区间。
- 区间非法（如 `x0 > x1`）时该层按「没有区间」处理，不抛错、不连累其它层。

### 「可走」只有一个来源

编辑器里所有连通性派生量（保存网格时的分块告警、孤立/被困诊断）都从
`web/static/js/grid/walk-policy.js` 里的 `WALK_POLICIES` 取判据，不再各自内联。

原因是踩过一次：分块告警过去用「节点认 `Free`、守卫只查 `Blocked`」这组**互不
匹配**的判据，于是报出来的块数在产品默认策略下偏少 —— map02 报 11 块、而规划器
（`allow_unknown=False`）看到 12 块，base01 报 5、看到 8。用户看到的数字和实际能
不能走过去对不上。**守卫判据必须与节点判据同源**：守卫更松时，斜向移动能借一个
未知格把两片可走区并起来。

两档策略各对应规划器的一档：`noUnknown` = `allow_unknown=False`（产品默认）、
`allowUnknown` = `True`。告警文案带上用的是哪一档，因为「分成几块」本身取决于
要不要冒穿过未知格的险，不是客观事实。

`tests/test_walk_policy_js.py` 的固定基线使用 `tests/data/walk_policy/` 中的真实网格
快照，不读取正在编辑的网格来断言历史数字。`baselines.json` 记录来源提交、原文件
SHA-256 和完整连通块大小列表：武陵主图 `1a23931` 为 14 块，`8f34d18` 增加两条
路线后为 16 块，两版最大块均为 32119 格；帝江号的异常数量也绑定固定快照。
这组检查无需子模块历史或 LFS 缓存，快照校验失败会直接报错，不跳过。

工作区武陵网格另做独立四连通交叉验证：严格策略的合法斜步都能替换为两步正交
移动，所以两种算法的完整连通分量大小必须相同。该参考算法只在测试中使用，
生产诊断仍统一走 `WALK_POLICIES`。更新固定基线时，须从明确的已提交版本复制
快照、记录 SHA-256，并独立复核期望值；不要直接用未提交网格的输出覆盖期望。
斜角相接、正交格是未知的最小反例仍保留，用于拦住旧判据错误合并两块的回归。

还要注意**块数会高估孤立**，而且偏差量是精确可算的：

```text
单格块数 = 真被困数 + 孤立数 + 假孤立数        （恒等，见测试）
```

「假孤立」指那格的对角有可行走邻居、而两个正交格被挡 —— 那是**我们自己的禁斜穿
规则造的孤立，游戏里人走得过去**。所以 `单格块数 == 被困 + 孤立` 等价于「假孤立
为 0」，是定理不是数据性质。实测 base01 是 `8 块 / 2 单格块 / 2 孤立 / 0 被困`
（假孤立 0），其余 4 张网格单格块全为 0。

结论：块数不能当「有多少格不连通」的另一种说法读，判断"某个格子是不是误点"要用
格子级的邻居事实（`walkableAnomalies`），不是块。

带分层的网格文件名为：

```text
<地图>__<tier>_<zoom>.grid.npz
```

未选择分层时继续使用旧格式：

```text
<地图>_<zoom>.grid.npz
```

**主图的 tier 有两种拼写，转换只走 `disk_tier` / `api_tier`（JS 侧是
`grid/tier-id.js` 的同名函数），别再内联判断：**

| 口径 | 值 | 用在哪 |
| --- | --- | --- |
| API | `"__main__"` | `/api/nav-graph`、`/api/grid2d/floor-map`、SSE 的 `gridTierId`、`/api/grid2d` 的 `tier` 参数 |
| 落盘 | `""` | 文件名与 `meta.tier`（`map02_4.grid.npz`，不带 tier 段） |

两种都必须存在：文件名里不能出现 `__main__`，而 API 里空串又表达不出「就是主图」
而不是「没选分层」。**少了转换是真的会出事** —— `valid_grid_tier("__main__")` 是
`True`（它符合地图名白名单），所以校验拦不住，落盘路径会拼出
`map02____main___4.grid.npz` 这种谁也不认识的伪文件名。这条转换以前散在 14 处内联
三元里，必然漏；现在 `tests/test_tier_spelling.py` 与
`tests/test_tier_id_js.py`（含一条源码级守卫）盯着它。

### 层声明索引 `levels.json`

导航网格目录里除了网格与 `links.json`，还有一份 `levels.json`：

```json
{
  "schema_version": 1,
  "generated_at": "…",
  "note": "level_id → 层 的**声明**索引（含还没有网格文件的层）…",
  "layers": [
    {"id": "scene_map02_lv005_layer_tips_7", "map_name": "map02",
     "level_id": "map02_lv005", "name": "测试区", "group": "测试区",
     "map_category": "layered"}
  ]
}
```

它解决的问题：分层目录 `catalog.json` 是 `fetch-layers` 的可重生本地缓存、**不进
版本库**，所以消费侧拿不到「哪个 level_id 声明了哪些层」，只能按网格文件反推 —— 而
map02 的目录里有 **9 个 level_id**、通常只有一两个有网格，按文件反推会把不同
level_id 的层混成一批候选，对跟随器就是静默错层。

所以这份索引把该**声明**物化进数据仓库（**包含还没有网格文件的层** —— 消费侧正是
靠它把「声明了但没有网格」与「这张图压根没有分层」分开）。某层是否真有网格仍要看
网格文件，索引只说明官方声明了哪些层。

由编辑器在**保存网格时**从分层目录自动刷新（内容没变就不写，免得在版本库里一直
脏）；分层目录不存在时**拒绝写** —— 那时只能退回内置的兜底目录，拿 7 条去覆盖完整
索引就是数据丢失。

## 2D 网格格式

网格以稠密 `uint8` NPZ 保存，文件名为 `<地图>_<zoom>.grid.npz`。
文件仅包含两个成员：

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| `cells` | `(H, W)` `uint8` | 行对应世界 z，列对应世界 x |
| `meta` | JSON 字符串 | 标定原点、格子尺寸和格式版本 |

`meta` 包含 `origin`、`cell_size`、`magic`、`schema_version` 和
`axis_convention`。`origin` 表示 `cells[0,0]` 最小角的世界坐标。

分层网格还可以在 `meta.floor_regions` 中保存三维高度区间。服务端收到位置流
坐标后，用这些区间判断玩家所在楼层：

```json
{
  "floor_regions": [
    {
      "x0": -768, "x1": 128,
      "z0": -768, "z1": 0,
      "y_min": 245, "y_max": 285
    }
  ]
}
```

只更新某个网格的楼层区间，不重存格子数据：

```powershell
$body = @{
  map = "map02"
  zoom = "4"
  tier = "scene_map02_lv005_layer_tips_7"
  floor_regions = @(
    @{ x0 = -768; x1 = 128; z0 = -768; z1 = 0; y_min = 245; y_max = 285 }
  )
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -ContentType "application/json" `
  -Body $body http://127.0.0.1:8877/api/grid2d/floor-regions
```

SSE `coords` 事件会带上判定结果：`gridFloorStatus`（`unique` / `ambiguous` /
`main` / `invalid`）、`gridTierId`、`gridFloorReason`（`region_hit` / `overlap` /
`no_layers` / `no_region_covers` / `invalid_map` / `invalid_position`）与
`gridFloorCandidates`。命中多层时是 `ambiguous`，服务端不会随便选择楼层；没有分层
重叠时是 `main`（大地图），这才是当前数据下的常态 —— 判定规则见上文「坐标 → 第
几层」一节。
网格或连接模式中的“楼层区间”按钮会自动叠加同一区域的候选楼层：绿色为当前层，
红色为 X/Z 与 Y 都重合，黄色为只有 X/Z 重合。先选择“重合连通区”，再选择
“重合地图网格”，分别填写该层的 Y 范围并保存。所有涉及层级都已定义高度的
连通区会改为蓝色，与未处理的黄色重合区区分。主地图以 `__main__` 作为
特殊网格参与重合分析，可以与任意分层网格一起设置高度区间。

保存范围取“原数组范围与已涂格子范围的并集”，因此已有未知边框不会被裁掉。
当前限制：

- 单次编辑最多保存 `300,000` 个已涂格子。
- 稠密数组跨度最多为 `64,000,000` 个格子。
- 写入前会执行一次完整读回校验，校验失败时不会覆盖原文件。

## 编辑会话与性能

### 同步数据仓库

点击顶部“同步仓库”后，编辑器会要求确认一次。服务端随后从
`assets/nav-grid-data` 的 `origin` 获取默认分支，强制检出远端最新提交并执行
`git clean -ffdx`，因此本地网格、`links.json`、`levels.json`、定位资源以及本地提交
都会以远端仓库版本为准。数据包中的 WebP/PNG/NPZ 使用 Git LFS，本机必须安装 Git LFS；
同步只对远端变更、本地脏文件和缺失的 LFS 路径读取指针中的 SHA-256 与大小，
下载这些文件后逐份校验，不会重新拉取整个分支的 LFS 内容，也不能只留下 LFS 指针。

同步成功后浏览器会清除 IndexedDB 网格草稿、刷新页面，服务端也会清空网格和分层缓存。
该按钮只执行仓库同步，不提交、不推送，也不会尝试合并本地数据。使用
`--grid2d-dir` 指向其他目录时，该目录必须正好是数据仓库根目录。

### 审阅 data PR

点击顶部“审阅 data PR”，下拉框会分页获取数据仓库全部 open PR（含草稿），选择后直接加载；可点击“刷新”重新获取。也可输入 PR 编号（如 `2`）或 GitHub PR 链接，再点击“加载 data PR”。列表为空或获取失败时仍可手动输入。
网格目录必须是带 GitHub `origin` 的 Git 仓库，本机需安装 Git 和 Git LFS。读取 PR 时优先复用本机 GitHub CLI 的已有登录；未安装或未登录时使用公开 GitHub API。匿名 API 限流时，安装 GitHub CLI 并执行 `gh auth login` 后重试；编辑器不保存账号凭证。

- 自动取得目标分支与 PR head 的共同祖先，固定并显示比较的两个 SHA；再次加载会检查最新版本。
- 自动下载真实 LFS 网格，校验 NPZ 格式与 `dataset.json` 中的文件大小、SHA-256；快照写入 `output/pr-review/`，不 checkout、不修改当前网格或子模块指针。
- 默认在本地底图上突出变化格，可切换“修改前 / 修改后 / 地图差异”、调节透明度；鼠标悬停显示 X/Z 和状态变化。
- 审阅面板优先展示变化格、可走格增减、连通块和待确认项；格式与清单检查通过项默认折叠。对比工具固定在地图底部，收起侧栏后仍能切换视图和变化区。审阅时隐藏采集与编辑工具，关闭后恢复。
- 支持 `J / K` 切换下一个 / 上一个变化区，`1 / 2 / 3` 切换差异 / 修改前 / 修改后，`F` 定位、`H` 收起或展开面板、`Esc` 退出；输入框内不触发快捷键。同一浏览器会记住上次成功加载的 PR 编号、对比视图和透明度。
- 相邻变化格组成变化区；自动选择地图/分层并定位，可通过下拉框或上一个/下一个按钮逐区查看。
- 检查摘要包括六种状态转换、坐标与高度元数据变化、可走格数量、严格策略下的连通块、孤立/被困格，以及连接与层声明的增删改数量。连通块增加只提示确认用途，不直接判定独立路线错误。
- 审阅快照只读，关闭后恢复原视图和编辑文档。差异按世界坐标对齐；格子尺寸或原点无法对齐时提供前后视图并明确提示，不自动重采样。独立场景本版仅展示摘要，不叠到大地图。
- 本版最多读取 20 份变化网格、前后合计 100 万已涂格；审阅栅格按可见区域解码，三种视图共用 32 MiB 缓存。不提供 GitHub 评论发布或批准操作；多 PR 合并见下文。

### 网格三方合并

在“审阅 data PR”的“选择多个 PR · 联合预览”中勾选 PR，再点击“联合预览”。
队列留空时使用当前 PR，也可输入多个编号（例如 `4, 5, 6`），按队列中的依赖顺序串行合并，最多 10 个 PR、
20 份变化网格。所有 PR 必须处于 open 状态并指向同一目标分支版本。

- 比较共同祖先、当前主线和 PR 版本；当前主线包含队列里此前已处理的 PR。
  同一格只有一边改变时采用该改动，两边改成相同状态时自动合并，改成不同状态时形成冲突。
  擦除为未知同样参与比较，不会用可走格并集覆盖阻挡或擦除。
- 网格按世界坐标对齐，支持整数格原点移动与扩图，保留未知边框。并发修改中出现
  坐标空间不兼容、范围收缩或删除与修改冲突时，要求明确选择整份网格，不隐式重采样。
- 相邻冲突格按区域显示；选择区域会定位地图，可切换共同祖先、当前主线、此 PR、
  合并结果和地图差异。未解决时预览暂用当前主线，导出按钮禁用。可以按区域采用
  当前主线、此 PR 或恢复共同祖先。前一 PR 的冲突未处理完，不继续后面的 PR。
- 全部 PR 处理完成后，地图差异展示目标分支到最终合并结果的全部变化，而非仅最后一个
  PR 的变化；文件摘要列出参与该文件合并的 PR。
- `floor_regions` 按整体字段三方比较；连接与层声明按稳定 ID 合并，保留现有字段。
  发布清单按记录身份合并，导航文件大小与 SHA-256 在导出时重新计算。
- “导出合并结果”会重新检查所有 PR head 和目标分支 SHA，并校验连接端点；版本变化、
  未解决冲突或无效端点会阻止导出。新网格如缺少发布清单的坐标绑定，需要先补全清单。
  服务重启或会话被淘汰后需要重新预览；服务最多保留两份合并会话。
- ZIP 中 `files/` 是合并后的变更文件，`merge-plan.json` 记录目标 SHA、PR 顺序、
  原始 head、冲突选择、删除列表及文件校验值。它是增量合并包，不是完整数据包。
  合并快照与导出文件位于 `output/pr-merge/`，现有 NPZ/JSON 结构保持不变。

冲突全部解决后，可直接点击“提交并推送，创建集成 PR”。界面会显示目标仓库、
目标分支和包含的 PR；服务端使用本机已登录的 GitHub CLI，账号需要数据仓库的
推送权限，仓库需要允许 merge commit。提交作者沿用本机数据仓库的 Git 配置。

- 在 `output/pr-publications/` 的独立 Git 仓库中按队列逐个创建合并提交：每个提交的
  两个父节点分别是上一步集成结果和原 PR head。原工作区、索引和子模块指针保持不变。
- 显式下载原 PR 历史所需的 LFS 对象并上传合并对象，再推送唯一的
  `codex/grid-merge-*` 分支。只允许新建分支或复用相同提交，拒绝覆盖远端不同内容。
- 提交、推送和创建 PR 前重新检查原始 head 与目标 SHA；发布是后台任务，界面显示
  当前阶段。进入发布后该份选择被冻结，需要修改时重新预览。
- 发布记录保存在本地，重试复用原分支和提交。推送成功但创建 PR 失败时可以继续创建；
  创建成功但响应丢失时会查找已有 PR，不重复创建。同一浏览器标签页刷新或关闭审阅
  后再次打开，会恢复最近一次发布状态。服务重启后已经完成的提交可继续发布；若提交
  尚未完成且原合并会话丢失，需要重新预览同一组 PR。
- 成功后显示集成 PR 链接和“确认合入 <目标分支>”按钮。点击后重新检查源 PR、目标分支
  和集成 PR 的版本，再通过 GitHub 的普通 merge commit 合入，保留原 PR 祖先关系。
  不自动合入，不绕过分支保护或必需检查；版本变化时需要重新预览，失败原因显示在界面。
  合并响应丢失时再次点击会查询实际状态，避免重复操作。也可在 GitHub 使用
  **Create a merge commit**。数据合入后再更新编辑器仓库的子模块指针。

### 从本地修改新建数据 PR

点击顶部“新建 PR”（窄屏可用 `Ctrl+K` 搜索“新建数据 PR”），先保存网格，选择提交账号，
再点击“检查已保存修改”。勾选要提交的导航文件后重新检查，填写标题，点击“提交并推送，创建 PR”。

- 账号下拉框来自本机 GitHub CLI 已登录的 `github.com` 账号。新增账号请在终端执行
  `gh auth login --hostname github.com --web`，完成浏览器登录后刷新账号列表。
  不使用浏览器当前登录账号，也不允许填写别人的用户名冒充提交者。
- 所选账号同时用于 Git/LFS 推送、创建 PR、Git 作者和提交者；作者邮箱使用
  `<GitHub 数字 ID>+<账号>@users.noreply.github.com`。不修改全局 Git 作者或 `gh` 默认账号。
  令牌仅保留在服务端内存并传给本次子进程，不返回网页或写入发布记录。
- 账号必须对数据仓库有推送权限；本入口暂不自动创建 fork。其他账号失效不会阻止所选
  有效账号提交；网络或认证失败会保留任务供重试。
- 只收集已保存到磁盘的根目录 `*.grid.npz`、`links.json`、`levels.json`、`dataset.json`。
  包含新增、修改、删除，以及本地分支尚未合入的导航修改；其它文件不提交。
  浏览器未保存草稿需要先保存；“保存全部网格”不会替你保存未完成的连接编辑或标定操作。
- 以本地 HEAD 与远端默认分支的共同祖先为提交基线，保留本地修改的原始语义。
  不把旧本地快照覆盖到最新主线；已经被主线吸收的修改会省略。若双方修改有冲突，
  创建 PR 后通过现有三方合并审阅处理。
- 在 `output/local-publications/` 独立目录构建普通单父提交，更新清单大小与 SHA-256，
  校验网格和连接端点，再推送 `codex/local-grid-*` 并创建 PR。原网格、索引、分支与
  编辑器子模块指针保持不变。新网格需要 `dataset.json` 中已有对应坐标绑定。
- 检查后文件、账号或目标分支有变化时需要重新检查。重试复用同一分支和提交；
  PR 创建成功但响应丢失时会查找已有 PR。刷新页面后可恢复发布状态；服务重启前尚未
  生成提交的任务需要重新检查文件。这个入口只创建 PR，之后可在审阅界面处理合并。

### 编辑与缓存

- 界面沿用黑底荧光绿配色，采用画布优先的简洁工作台布局。顶部用独立下拉框选择主图、分层和级别；点击画布上的分层入口或返回上一分层时，下拉框同步当前层。3D 与属性开关位于左侧模式按钮旁，工具属性默认在画布左侧弹出；没有遮罩、不占布局列，打开时仍可在其余画布区域绘制、平移和缩放。模式与画笔在画布上方，视图导航在下方，保存固定于页面右上角；属性面板开合不改变画布尺寸、中心或缩放。
- 顶部“工作空间”集中采集、地图标记、导出、日志与数据管理。`Ctrl+K` 搜索命令，方向键选择、回车执行；窄屏也可从命令搜索进入审阅与导出。弹窗限制焦点在窗口内，`Esc` 关闭；同步仓库必须在确认窗口明确确认，取消不发送同步请求。
- 属性面板随模式切换：浏览时调整显示图层，网格时配置抓包自动标记，连接时编辑两端高度，标定时管理控制点，坐标模式显示读数。网格参数与草稿、路径预览及导航检查默认折叠。框选后展开填充工具；自动标记开启后工具栏显示停止入口。楼层高度、坐标定位和快捷键说明使用独立弹窗。当前地图有未保存网格时，清空画布会被阻止。
- 布局参考 [Linear 的界面简化](https://linear.app/now/behind-the-latest-design-refresh) 与 [Figma UI3 的画布和面板设计](https://www.figma.com/blog/our-approach-to-designing-ui3/)。工作台交互独立在 `workbench.js`，共享控件在 `map_composer.css`，布局在 `workbench.css`；保留原生 ESM / Canvas，无新增前端构建依赖。3D 视图按实际可见画布尺寸渲染，右侧属性不遮挡场景。
- 每个地图、zoom、分层分别保留编辑文档与撤销历史；保存后仍可撤销，跨层返回不会丢掉未保存修改。强制重新载入不会覆盖未保存文档。
- 未保存网格在停止操作约 1.5 秒后备份到当前浏览器的 IndexedDB；打开对应地图/层后点击“恢复当前层草稿”。恢复不会自动写入导航文件。浏览器存储被清除后草稿也会消失，关闭页面前仍应保存。
- 所有模式均可使用适应窗口、上一分层、分层下拉框、X/Z 定位和快捷键提示。画笔提供宽度预设，30 万格范围内的批量填充分片执行并显示进度。
- 高度对话框可同时勾选多个层填写区间并提交；选择目标层不会强制切画面。空高度不再当作零，网格保存保留磁盘上最新的高度标注。
- 连接草稿退出模式后保留，起终点可单独定位；Ctrl+S 在连接模式保存连接。导出面板列出未保存文档，提供“保存全部并导出”；保存失败时不会启动导出。
- 连通性诊断在模块 Worker 中执行，过期诊断不更新当前文档。撤销历史按 100 次和约 32 MiB 预算限制；每个地图最多缓存 12 个已保存层文档，未保存文档不淘汰。
- 分层图由服务端生成最长边 2048 的预览，放大后只请求可见的 1024 像素原尺寸分块。分块与底图共享 96 MiB 解码缓存和最多 6 个并发请求，切换地图会取消旧请求。服务端只保留一个解码分层源图及最多 16 MiB 编码衍生图缓存。
- 滚轮缩放与拖动越界重绘按动画帧合并；缓冲区内拖动只更新位移，不重画栅格。低缩放的底图预览只绘制一次，空路径和空连接图层释放为 1×1 画布。窗口大小、选区工具条变化由实际视口尺寸观察器驱动重绘。分层下拉框直接使用编辑器状态，不维护重复的分层列表，界面不使用实时背景模糊。3D 窗口关闭或切换分层组后，过期加载不再重建旧场景；晚到的纹理会释放，关闭后不会重启隐藏的动画循环。
- 调试统计 `window.__NAV_GRID_EDITOR__.stats` 包含分块/预览/画布字节估计、网格栅格缓存及历史估计，以及 `renderFrames`、`renderLastMs`、`renderTotalMs`（绘制次数与主线程绘制耗时，不是 GPU 完成时间）。字节估计不等于操作系统实际显存或进程内存。
